# environmentsentry — Usage Guide

Complete examples for integrating environmentsentry into your projects.

---

## 1. Install

```bash
# Global (recommended for CLI)
npm install -g environmentsentry

# Or locally in your project
npm install environmentsentry
```

---

## 2. Initialize a project

Create a `.env.sample` listing all variables your app needs:

```bash
# .env.sample
NODE_ENV=development
PORT=3000
DATABASE_URL=postgres://localhost:5432/mydb
API_KEY=
JWT_SECRET=
```

Then generate a `.env` from it:

```bash
environmentsentry fix -e .env.sample
```

This creates `.env` with all required keys (empty values, ready for you to fill in). It never overwrites existing values.

```bash
# Fill in real values in .env, then verify:
environmentsentry check
```

---

## 3. Check environment variables

```bash
# Basic check (styled table output)
environmentsentry check

# Check with custom file paths
environmentsentry check -f .env -e .env.sample

# JSON output (for CI/CD scripts)
environmentsentry check --json

# Exit with code 1 if any issues (useful in pre-commit hooks)
environmentsentry check --strict

# Watch mode — re-scan every 2 seconds (Ctrl+C to stop)
environmentsentry check --watch

# Include/exclude specific files
environmentsentry check --include "*.ts" --exclude "node_modules"
```

## 4. Scan source code for env usage

```bash
# Scan all source files for process.env.VAR references
environmentsentry usage

# JSON output
environmentsentry usage --json

# Watch mode (live re-scan)
environmentsentry usage --watch

# Filter by file type
environmentsentry usage --include "*.ts" --exclude "node_modules"
```

### Example output


## 5. Generate `.env.sample` from source usage

```bash
environmentsentry example
```

This scans your source code, finds every `process.env.VAR`, and creates a `.env.sample` with comments showing where each variable is first used.

```bash
# Custom output path
environmentsentry example -o .env.example

# Filter files
environmentsentry example --include "*.ts" --exclude "node_modules"
```

### Example generated `.env.sample`

```env
# Generated by environmentsentry from source-code usage
# Do not commit real values. Fill in values before deploying.

# Used in: src/config.ts:12
DATABASE_URL=

# Used in: src/services/auth.ts:5
API_KEY=

# UNUSED: NODE_ENV=
```

## 6. Production environment setup

```bash
# Validate, create .env.production, and run tests
environmentsentry prod

# Force overwrite existing .env.production
environmentsentry prod --force

# Custom root directory
environmentsentry prod -r ./my-app
```

This:
1. Validates all env vars against `.env.sample`
2. Creates `.env.production` with empty values ready for production
3. Runs `npm test` to verify nothing is broken

## 7. Secure vault (AES-256-GCM encrypted)

Store sensitive values in an encrypted local SQLite database instead of plaintext `.env` files.

```bash
# Initialize vault (prints encryption details)
environmentsentry vault init

# Store a value (encoded at rest)
environmentsentry vault set DATABASE_URL "postgres://user:pass@localhost:5432/db"

# Retrieve value (masked by default)
environmentsentry vault get DATABASE_URL
# Output: ****  (sha256: a1b2c3d4e5f6…)

# Retrieve with plaintext (--reveal required)
environmentsentry vault get DATABASE_URL --reveal

# List all keys (no values exposed)
environmentsentry vault list

# Show encryption algorithm details
environmentsentry vault info

# Remove a key
environmentsentry vault remove DATABASE_URL
```

### Security properties

| Property | Value |
|---|---|
| Cipher | AES-256-GCM |
| Version | v1 |
| Key derivation | PBKDF2-HMAC-SHA256 |
| Iterations | 210,000 |
| Key length | 256-bit |
| Salt | 16 bytes (random per value) |
| IV | 12 bytes (random per value) |
| Auth tag | 16 bytes (GCM) |
| Console output | Masked by default (`****` + sha256 hash) |
| Plaintext reveal | `--reveal` flag required |

Values are encrypted at rest in `.environmentsentry-vault.sqlite`. Plaintext never touches the console unless you explicitly pass `--reveal`.

## 8. Multi-project scan (monorepos)

```bash
# Scan all projects under a root directory
environmentsentry scan -r . -d 3

# JSON output for CI
environmentsentry scan --json

# Exit with code 1 if any project has issues
environmentsentry scan --strict
```

Treats any folder containing `.env.sample` or `package.json` as a project. Skips `node_modules`, `.git`, `dist`, `build`, etc.

---

## 9. Explain a failed command

```bash
environmentsentry explain -c "npm run build"
environmentsentry explain -x 1 -s "Cannot find module 'dotenv'"
environmentsentry explain -s "EADDRINUSE: address already in use :::3000"
```

Returns plain-English cause, likely file, and step-by-step fix.

## 10. Complete workflow example

```bash
# 1. Initialize project
cd my-app
environmentsentry fix -e .env.sample

# 2. Fill in real values in .env (never commit .env)

# 3. Verify all variables
environmentsentry check

# 4. Check source code usage
environmentsentry usage

# 5. Generate/update .env.sample from actual usage
environmentsentry example

# 6. Store sensitive values in vault
environmentsentry vault init
environmentsentry vault set DATABASE_URL "postgres://prod:secret@db:5432/app"

# 7. Production deploy
environmentsentry prod --force

# 8. Add to CI/CD (pre-commit hook)
environmentsentry check --strict
```

## 12. CI/CD integration

Add to your `package.json` scripts:

```json
{
  "scripts": {
    "env:check": "environmentsentry check --strict",
    "env:fix": "environmentsentry fix",
    "env:usage": "environmentsentry usage",
    "predeploy": "npm run env:check"
  }
}
```

Add to GitHub Actions (`.github/workflows/env-check.yml`):

```yaml
name: Env Check
on: [push, pull_request]
jobs:
  env-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-node@v3
        with:
          node-version: '18'
      - run: npm install -g environmentsentry
      - run: environmentsentry check --strict
```
